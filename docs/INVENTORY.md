# SoloCollections 资料与实现清单

本文是统一仓库建立时的基线清单。它回答“目前到底有什么、完成到哪一步、
哪些可以公开、后续从哪里继续开发”。

## 一、源码组成

### 1. WoW AddOn

目录：`addon/SoloCollections`

- 入口与生命周期：`SoloCollections.lua`、`Core/Bootstrap.lua`
- 静态目录与查询：`Data/*.lua`、`Core/Catalog.lua`
- 客户端通信：`Core/Bridge.lua`
- M2 镜头参数：`Core/M2Camera.lua`
- 公共界面：`UI/Templates.lua`、`UI/CollectionsFrame.lua`、`UI/Launcher.lua`
- 页面：坐骑、小宠物、玩具、外观/套装
- 媒体：`Media`，当前保留项目自制素材和已记录的客户端提取素材

当前静态数据基线：

| 类别 | 数量 |
| --- | ---: |
| 坐骑 | 24 |
| 非战斗小宠物 | 24 |
| 玩具 | 36 |
| 外观 | 70 |
| 套装 | 8 |

这些数据提供演示和 UI 开发，不等于完整服务器收藏数据。

### 2. AzerothCore ALE 服务端桥

文件：`server/ale/solo_collections.lua`

已有能力：

- SC1 握手和功能声明；
- 坐骑/宠物模型缓存请求；
- 演示召唤和玩具动作；
- ID 白名单、状态校验、玩家级限流和明确错误响应。

未完成能力：

- 账号级持久化收藏表；
- 获取方式与真实解锁钩子；
- 登录全量同步和增量同步；
- 完整外观/套装后端；
- 生产级数据迁移、管理命令和运维监控。

因此当前服务端文件应称为“演示/动作桥”，不能宣传成完整收藏服务。

### 3. SoloCam 客户端扩展

目录：`client-extension/SoloCam`

- `src`：32 位 C++ DLL 和硬编码客户端地址；
- `poc_patch.py`：复制并修补用户自己的客户端 EXE，使副本加载 DLL；
- `scripts`：编译、部署和武器资源研究管线；
- `tests`：镜头、显示信息、地址和补丁器测试；
- `requirements-dev.txt`：`capstone==5.0.6`、`pefile==2024.8.26`。

支持边界：

- 仅 x86；
- 仅精确的 WoW 3.3.5a build 12340；
- 锁定原始 EXE SHA-256：
  `AA63A5750D60EF16746C686B3D5E26876D98953EAB08B1C026CD0FAF78E88CB8`；
- 当前角色装备镜头重点覆盖人类女性 9 个护甲部位；
- 主手/副手通过独立显示信息和模型桥处理；
- 补丁器生成 `Wow-SoloCam-PoC.exe`，不覆盖原 `Wow.exe`；
- Git 和 Release 永远不包含原版或已修补的游戏 EXE。

这部分是真正涉及客户端注入和固定地址的高风险组件，必须独立标注为可选
PoC，并对每个客户端版本失败关闭。

### 4. 测试、部署和研究工具

目录：`tools/collections`

- 122 项 AddOn、目录、Bridge、媒体、部署和 M2 研究契约测试；
- 安全部署脚本支持 `-WhatIf`、目标冲突检查、备份、事务回滚和哈希验证；
- `m2_camera_patch.py` 只用于离线格式研究；已证明给玩家 M2 增加第三镜头会
  导致客户端 `ERROR #132`，不应作为正式路线。

SoloCam 另有 Python 和原生 C++ 测试。依赖真实 `Wow.exe` 的测试通过环境变量
选择用户本地文件；CI 中没有文件时会明确跳过，不会下载或伪造游戏文件。

## 二、文档

- `docs/architecture`：当前架构和实现说明，应优先阅读；
- `docs/history`：原设计与实施计划，保留当时绝对路径作为历史证据，不能直接
  当作当前命令；
- `docs/DEVELOPMENT.md`：统一仓库开发、测试和部署流程；
- `docs/ASSETS.md`：占位素材和网盘同路径覆盖策略；
- `docs/LICENSING.md`：公开前许可证待办；
- `THIRD_PARTY_NOTICES.md`：第三方代码和素材来源审计表。

## 三、素材现状

`addon/SoloCollections/Media/assets.json` 已记录素材尺寸、用途、SHA-256 和已知
来源。当前明确是混合状态：

- 项目自制 TGA：背景、边框、页签和启动图标，可作为占位素材候选；
- `Media/Retail`：包含明确记录的 Retail 客户端/CASC 衍生文件，当前只为本地
  开发保留，尚未获准作为公开仓库内容。

首次公开前必须把后一类替换为项目自制或许可明确的同尺寸、同格式、同路径
占位文件，并更新 `assets.json`。网盘完整素材包保持相同目标路径，用户可以
直接覆盖。素材包必须有兼容项目版本、独立许可证、安装/卸载说明和 SHA-256
清单。

## 四、未归入源码的内容

旧工作区 `_work` 中的以下内容没有复制进 Git 源码：

- 客户端原始或提取的 MPQ、DBC、M2、SKIN、BLP 批量资源；
- 编译缓存、第三方二进制依赖目录和生成的 DLL/EXE；
- 临时回读校验目录、部署备份和现场运行副本。

这些是生成物、私有输入或本机缓存。构建脚本和依赖清单已归仓，生成物应由
开发者在本地重新产生。

## 五、源码与 Release 目标

源码仓库应包含所有可审计源码、测试、文档和公开占位素材。Release 分为：

1. 可直接解压到 `Interface/AddOns` 的 AddOn zip；
2. 可部署到 ALE 脚本目录的服务端 zip；
3. 可选 SoloCam win32 zip，只含项目 DLL、补丁工具和说明；
4. 网盘提供的可选完整素材覆盖包。

当前代码可继续开发，但首次公开发布仍被两个事项阻挡：最终代码许可证和公开
素材替换/来源审计。

## 六、继续开发的位置

唯一推荐位置就是本仓库。测试客户端、服务器目录和网盘素材源都是外部输入或
部署目标，不是源码。需要同时验证稳定版和新功能时，使用 Git 分支或 worktree；
不要复制一份源码长期开发后再整目录覆盖回来。
