# 01 收藏系统总体架构

## 1. 目标与范围

SoloCollections 用一个独立插件在 WoW 3.3.5a 中重建正式服收藏日志的主要体验。第一阶段包括坐骑、小宠物、玩具箱、外观物品和外观套装，不包含战斗宠物。

这套架构刻意把 UI、目录数据和服务端权限分开。客户端可以先用演示数据搭界面，之后把解锁、召唤和使用权限迁移到服务端 Lua，再迁移到 C++ 模块，不必重写 UI。

## 2. 当前分层

```text
Data/*.lua
    ↓
Core/Catalog.lua       查询、过滤、分页、收藏与偏好解析
    ↓
UI/*.lua               只负责展示和交互
    ↕
Core/Bridge.lua        AddOnMessage 请求/响应原型
    ↕
服务端 Lua / C++       最终权限、解锁、持久化与执行
```

### Data 层

目录文件：

- `Data/Mounts.lua`
- `Data/Pets.lua`
- `Data/Toys.lua`
- `Data/Appearances.lua`
- `Data/Sets.lua`

记录至少需要稳定的 `id`、显示名称、来源、描述和类型专属字段。外观记录还需要 `itemId`、`slot`、职业限制；武器记录需要独立模型桥字段。

不要把收藏状态只写死在 Data 文件。演示阶段可以存在 `collected` 默认值，但生产状态应由服务端同步后覆盖。

### Catalog 层

`Core/Catalog.lua` 是所有页面共用的数据入口：

- 按分类取得数据。
- 复制记录，避免 UI 直接污染静态目录。
- 搜索名称、来源和描述。
- 已收集/未收集过滤。
- 偏好过滤。
- 外观职业和部位过滤。
- 分页和进度统计。
- 从 SavedVariables 解析偏好覆盖。

未收集坐骑和小宠物在 Catalog 层直接视为不可偏好，避免 UI 漏判。

### Bridge 层

`Core/Bridge.lua` 当前使用前缀 `SC1` 和自发 Whisper AddOnMessage 建立通信原型，包含：

- `HELLO|1`
- `MODEL|requestId|mountId`
- `SUMMON|requestId|mountId`
- `PET_MODEL|requestId|petId`
- `PET_SUMMON|requestId|petId`
- `TOY_USE|requestId|toyId`

对应响应格式：

- `HELLO_ACK|1|DEMO`
- `MODEL_READY|requestId|mountId`
- `SUMMON_RESULT|requestId|ACCEPTED|mountId`
- `SUMMON_RESULT|requestId|ERROR|REASON`
- `PET_MODEL_READY|requestId|petId`
- `PET_SUMMON_RESULT|requestId|ACCEPTED|petId`
- `PET_SUMMON_RESULT|requestId|ERROR|REASON`
- `TOY_USE_RESULT|requestId|ACCEPTED|toyId`
- `TOY_USE_RESULT|requestId|ERROR|REASON`

每类请求都有独立 pending 表、递增 request ID、超时和回调。响应必须校验前缀、频道、发送者、请求 ID 和业务 ID。

重要：当前 `Bridge` 仍将 `demoMode` 保持为 true，它是客户端通信契约的原型，不代表服务端收藏系统已完整完成。

当前演示服务端入口为：

```text
server/ale/solo_collections.lua
```

该文件包含固定坐骑、宠物、玩具表、限流、查询预热、召唤和玩具施法，仍是演示 action bridge。它没有账号收藏表、拾取解锁 hook、登录全量同步，也没有外观收藏后端。不要把它当成生产实现。

目前协议也没有定义“服务器向客户端同步完整收藏列表”的消息。生产版应另行设计带版本、分片、总数和完成标记的同步协议，或让客户端目录保持静态、服务端只同步已解锁 ID 集合。

### UI 层

`UI/Templates.lua` 提供公共控件，页面文件只实现本页布局和行为：

- `UI/Mounts.lua`
- `UI/Pets.lua`
- `UI/Toys.lua`
- `UI/Wardrobe.lua`
- `UI/CollectionsFrame.lua`
- `UI/Launcher.lua`

## 3. 服务端最终职责

生产实现必须由服务端负责：

1. 判断物品拾取、学习或奖励是否触发解锁。
2. 将收藏状态写入账号级或角色级数据库。
3. 登录时同步收藏数据。
4. 校验坐骑、小宠物和玩具是否已解锁。
5. 执行召唤或玩具效果。
6. 实施冷却、地图、战斗状态和权限限制。
7. 防止客户端伪造收藏请求。

“玩具出售后仍可使用”的实现关键是服务端收藏表，不是客户端背包扫描。客户端卡片只发送 toy ID；服务端查询收藏记录后执行对应效果。

## 4. 建议的数据表

可先由服务端 Lua 使用自定义表，后续 C++ 继续复用：

```sql
CREATE TABLE account_collection_unlock (
    account_id INT UNSIGNED NOT NULL,
    collection_type VARCHAR(16) NOT NULL,
    collection_id INT UNSIGNED NOT NULL,
    unlocked_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (account_id, collection_type, collection_id)
);
```

若收藏按角色保存，将 `account_id` 改为角色 GUID。不要同时维护互不一致的账号表和角色表。

## 5. 新增收藏分类的步骤

1. 在 `Data` 新建分类目录。
2. 在 `Catalog.CATEGORY_KEYS` 注册分类。
3. 明确搜索字段、过滤字段和收藏统计口径。
4. 在 `CollectionsFrame` 注册页面和主标签。
5. 在 Bridge 添加请求、pending、超时、响应校验。
6. 在服务端实现同名协议。
7. 增加 SavedVariables 默认结构。
8. 分别测试断线、超时、非法 ID、未解锁和成功响应。

## 6. 验收标准

- UI 在服务端不可用时能进入明确的演示/降级状态，不发生 Lua 错误。
- 搜索、过滤和进度统计都通过 Catalog，不在每个页面复制算法。
- 客户端不能通过篡改 `collected=true` 绕过服务端权限。
- 同一个 request ID 只能完成一次回调。
- 超时请求会释放，不会无限积累。
- 收藏物品离开背包后，服务端收藏记录仍存在。

## 7. 不应采用的做法

- 把所有逻辑写进一个 Lua 文件。
- 由 UI 直接修改静态 Data 作为生产收藏状态。
- 客户端收到任意 AddOnMessage 就执行召唤。
- 将物品仍在背包作为玩具已解锁的唯一判断。
- 在服务端 Lua 阶段设计一种协议，迁移 C++ 时再全部推翻。
