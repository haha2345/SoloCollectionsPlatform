# 10 性能优化、测试方法与避坑

## 1. 性能问题的主要来源

收藏页最重的不是文字和纹理，而是同时存在的 `PlayerModel`/`DressUpModel`。外观页一页 18 张模型卡片，如果每次搜索、hover 或 `OnUpdate` 都重新 `SetUnit + TryOn`，会明显卡顿。

常见开销：

- 18 个模型同时异步装载；
- 每个模型独立永久 `OnUpdate`；
- 重复 `SetUnit("player")` 清空再换装；
- 页面切走后隐藏模型仍继续刷新；
- 物品信息未缓存时反复调用 `GetItemInfo`；
- 翻页时销毁并重建整页 frame；
- C++ bridge 为每次刷新创建不稳定记录。

## 2. 当前保留的优化策略

### 2.1 Frame 池固定复用

坐骑和宠物列表只创建可见行；玩具和外观页只创建每页需要的固定卡片：

- 玩具：18 个 tile；
- 外观：18 个 model card；
- 刷新时更新 record，不销毁重建 frame。

### 2.2 Generation 令牌

模型和 item info 都可能延迟完成。每次页面/过滤/翻页改变时增加 generation：

```lua
page.scGeneration = page.scGeneration + 1
local generation = page.scGeneration
```

异步回调执行前必须比较 generation 和 card 当前 record。旧任务直接丢弃，防止上一页模型写入新卡片。

### 2.3 只在 record 改变时重建模型

卡片刷新前比较稳定标识，例如：

```text
category + itemId + slot + appearance/display id
```

如果未改变，只更新收藏状态、hover 或文字，不重新 `SetUnit/TryOn`。

外观物品卡统一使用 Transmorpher 查询与 generation-safe 渲染队列：物品缓存
未就绪时只挂起对应记录，缓存完成后每个 UI 帧最多提交一张有效卡片。护甲和
武器继续复用固定的 18 个 `DressUpModel`；`OnUpdateModel` 只恢复动画 sequence，
不挂永久逐帧镜头恢复任务。

### 2.4 单一任务驱动器

不要给 18 张卡片各挂一个永久 `OnUpdate`。页面持有一个短生命周期任务队列：

1. 每帧处理有限数量模型任务；
2. 任务完成或 generation 失效后移除；
3. 队列为空时清除 `OnUpdate`；
4. 页面隐藏时清空任务并停止驱动。

### 2.5 分批加载

打开外观页时可先显示卡片边框、名称和已有缓存，再分帧初始化模型。目标不是瞬间完成所有 18 个模型，而是避免单帧峰值。

### 2.6 缓存事件驱动

`GetItemInfo` 返回空时记录 item ID，等待 `GET_ITEM_INFO_RECEIVED` 后只刷新相关卡片。不要用无限定时器轮询全部物品。

## 3. 收藏状态的用户体验

中途使用过覆盖整个卡片的半透明灰色遮罩，导致部分卡片像多了一层脏玻璃，也遮住装备细节。最终建议采用正式服式弱化：

- 已收集：正常亮度、金色名称或金色选中边框；
- 未收集：模型整体降低亮度或使用灰色文字；
- 右上角显示完整的“未收集”小标签；
- 不使用覆盖整个模型区域的大面积半透明矩形；
- hover 只改变细边框或轻微高亮，不显示小块蓝色法术按钮光效；
- 收藏星标和“未收集”标签不能重叠。

状态标签需给足宽度，不要通过字符串截断显示“未收...”。在卡片宽度有限时，优先使用字号更小的完整文字或明确图标，并在 tooltip 解释。

## 4. UI 测试方法

采用“一个页面/部位一个验收闭环”：

1. 对照正式服参考图确认构图目标。
2. 只修改一个 profile 或一个组件。
3. 编译、部署 PoC。
4. 用户在游戏内截图反馈。
5. 参数稳定后再进入下一部位。

不要一次改完所有 camera 再测试；不同 race、sex、模型包和部位的方向、偏移、
距离都可能不同。

### 每轮最小测试矩阵

| 维度 | 检查项 |
|---|---|
| 页面 | 坐骑、宠物、玩具、外观、套装 |
| 导航 | 搜索、过滤、翻页、切页、关闭重开 |
| 状态 | 已收集、未收集、偏好、无数据 |
| 模型 | 初次加载、连续切换、窗口移动、页面隐藏 |
| 输入 | 左键、右键、拖动、滚轮、ESC |
| 异步 | item cache 未命中、服务端超时、旧 generation |

## 5. 3.3.5 Lua 兼容性

不要假设正式服 Lua/API 可用。已遇到的直接例子是 `math.mod` 在目标客户端为 nil，应使用 `%` 或项目兼容函数。

提交前检查：

- Lua 语法是否适用于 5.1/3.3.5 客户端；
- 正式服 `C_*` 命名空间是否不存在；
- `CreateFrame` 模板是否为 3.3.5 内置模板；
- `GetItemInfo` 是否可能异步返回空；
- secure action、宏和拖动是否受战斗锁定影响；
- 模型 API 的参数语义是否由本地客户端实际验证。

正式服源码用于视觉结构和交互参考，不能直接复制正式服 API 调用。

## 6. 已验证失败或应避免的路线

### UI/Lua

- 直接复制正式服 XML/Lua，忽略 3.3.5 API 缺失；
- 用分页替代正式服风格可滚动坐骑列表；
- 对未收集坐骑/宠物开放偏好设置；
- 玩具必须留在背包才能使用，违背收藏语义；
- 大面积灰色遮罩覆盖未收集模型；
- 每次 hover 都重建模型。

### 角色局部模型

- 用屏幕坐标推导 camera；
- 让窗口位置参与模型缩放；
- 给角色 M2 追加第三个 camera；
- 每张卡片永久运行独立 `OnUpdate`；
- 不恢复客户端 render/camera 状态。

### 武器模型

- 把 `CreatureDisplayInfo.ID` 直接传给原生 `SetCreature`；
- 使用 NPC/怪物 entry 作为武器容器；
- 只用通用 `Model:SetModel` 加载需要 `OBJECT_SKIN` 的武器；
- 把黑模误判成 camera 问题；
- 为每件武器创建独立 MPQ；
- 把临时对象地址交给客户端。

### 工程

- 覆盖原始 `Wow.exe` 做试验；
- 以 x64 编译要注入 32 位 WoW 的 DLL；
- 使用未验证客户端版本的硬编码地址；
- 把编译缓存和临时打包文件写入 C 盘。

## 7. 构建和部署安全规则

1. 通过 `SOLOCOLLECTIONS_VCVARS` 或 `vswhere` 使用本机 Visual Studio Build Tools。
2. C++ 目标为 x86。
3. 中间文件放 `client-extension/SoloCam/build`。
4. 使用 `Wow-SoloCam-PoC.exe`，保留原始 `Wow.exe`。
5. 修改 MPQ 前保留原文件或生成可删除的独立 patch。
6. 客户端运行时不要覆盖 DLL/EXE；先退出客户端。
7. 部署前后记录原始 EXE、PoC EXE 与 DLL 的 SHA-256；脚本拒绝客户端 hash 或
   补丁点时不得手工绕过。

- [ ] 所有页面在无服务端响应时有明确降级提示。
- [ ] C++/SC2 是唯一生产写入者，ALE/SC1 仅用于迁移或对照。
- [ ] 主界面、底部标签、搜索、过滤、进度条风格一致。
- [ ] 已收集/未收集/偏好状态在所有页面含义一致。
- [ ] 模型切页后没有遗留 `OnUpdate` 或世界泄漏。
- [ ] 外观 18 卡片快速切换没有明显连续卡顿。
- [ ] SoloCam 单元测试通过。
- [ ] 主手/副手使用聚合 patch 和稳定 display 映射。
- [ ] 所有新文件位于项目盘，不写 C 盘。

## 9. 其他 AI 的推荐工作顺序

1. 先读 [01-收藏系统总体架构.md](01-收藏系统总体架构.md)。
2. 再读目标页面文档和对应源码。
3. 若涉及外观，先确认是角色部位还是独立武器。
4. 只改一个可验收单元。
5. 运行最小构建/语法检查。
6. 生成 PoC，明确列出需要用户在游戏里验证的截图。
7. 不在未经截图验收时批量改其他部位。
