# 01 收藏系统总体架构

本文描述 `main` 分支当前实现，而不是早期 SC1/ALE 演示方案。SoloCollections
由两个独立仓库组成：

- **SoloCollections**：客户端 AddOn、目录生成、SC2 协议规范和可选 SoloCam；
- **mod-solo-collections**：AzerothCore C++ 权威后端、数据库和服务端动作。

生产环境必须只有一个写入者：`mod-solo-collections` 以
`SoloCollections.Backend = Cpp` 运行。`server/ale` 中的 Lua/SC1 代码只用于旧版
迁移、对照和研究，不能与 C++ 后端同时拥有收藏写权限。

## 1. 数据与运行链路

```text
catalog/ 源清单
    │
    ├─> addon/SoloCollections/Data/Generated/*.lua
    │        │
    │        └─> AddOn UI、搜索、过滤、镜头身份和本地展示
    │
    └─> mod-solo-collections/src/generated/*.inc
             │
             └─> C++ provider、授权、动作和目录 hash

AddOn  <-- SC2 分片/修订同步 -->  C++ module  <-->  characters 数据库
```

目录的人工维护入口在 `catalog/`。生成后的 Lua/C++ 文件属于可复现的最终产物，
不应在两端分别手工修改。两仓库发布时必须使用相同的 metadata、mapping hash 和
presentation hash；不匹配时应拒绝或降级，而不是猜测兼容。

## 2. AddOn 的职责

AddOn 运行于 WoW 3.3.5a（Interface `30300`），负责：

- 收藏日志 UI、搜索、过滤、排序与进度展示；
- 读取静态目录和稳定 identity；
- 通过 SC2 接收账号收藏快照与增量；
- 向服务端发送请求并展示明确结果；
- 在服务端不可用、版本不匹配或超时时安全降级；
- 把身体部位/武器镜头意图交给可选 SoloCam。

客户端数据不是授权依据。修改 SavedVariables、生成目录或 UI 中的
`collected` 字段，不得绕过服务端校验、学习、召唤、使用或外观操作。

主要边界：

```text
addon/SoloCollections/Core/Catalog.lua          目录查询与过滤
addon/SoloCollections/Core/CollectionState.lua  客户端快照、revision 与状态
addon/SoloCollections/Core/Bridge.lua           SC2 transport
addon/SoloCollections/UI/                       页面与交互
```

## 3. SC2 协议

SC2 是当前 AddOn/C++ 模块之间的协议。规范见
[`docs/protocol/sc2-wire-v1.md`](../protocol/sc2-wire-v1.md)，machine-readable
schema 与 golden vectors 位于 `protocol/sc2/`。

协议实现必须保持以下性质：

- HELLO/ACK 明确版本、能力和目录 hash；
- 全量状态可分片，并带 generation、revision、总数和完成边界；
- 增量只在正确 revision 上应用，缺口触发重同步；
- request/response 同时校验发送者、请求 ID、类型和业务 ID；
- 重复包、旧包、超时包不能二次完成动作；
- 未识别版本或过大 payload 必须 fail closed。

不要给 SC2 添加只在 Lua 或只在 C++ 端存在的临时字段。协议、golden vector 和
两端解析器必须在同一次跨仓库变更中更新。

## 4. C++ 模块的职责

`mod-solo-collections` 是账号收藏状态的权威实现：

1. 检查数据库 schema 并加载账号快照；
2. 通过 provider registry 校验 mount、companion、toy、appearance、set 等类型；
3. 对解锁、撤销和动作做服务器侧权限判断；
4. 在同一事务/修订边界内写入收藏状态和审计记录；
5. 向在线会话发送 SC2 快照、增量和动作结果；
6. 记录可诊断但不泄露敏感数据的日志；
7. 在目录或协议不兼容时停止写入。

账号数据表及 revision 规则见模块仓库的
`docs/schema/account-collections-v1.md`。不要再建立第二套 AddOn、ALE 或角色级
“临时真相表”。

## 5. Backend 模式

`conf/transmog.conf.dist` 保留三种迁移模式：

| 模式 | 用途 | 是否推荐生产 |
|---|---|---|
| `Lua` | 旧 ALE/SC1 路线 | 否 |
| `Compare` | 只读对照和迁移观察 | 否 |
| `Cpp` | C++/SC2 单写者 | 是 |

新部署应先导入 schema、确认模块启动日志和 SC2 握手，再显式切换到 `Cpp`。
不能因为 AddOn UI 可以打开，就推断服务端收藏链路已经可用。

## 6. SoloCam 的位置

SoloCam 是可选的 32 位客户端显示扩展，只改善物品页身体部位和独立武器/
副手模型的构图。它不拥有收藏状态，也不参与授权。客户端 hash、构建和回退
边界见 [08-客户端SoloCam扩展.md](08-客户端SoloCam扩展.md)。

没有 SoloCam 时，AddOn 必须使用原生模型能力或显示“不可用”，不能崩溃，也
不能影响服务端功能。

## 7. 新增收藏类型或行为

一次完整扩展通常需要：

1. 在 `catalog/` 定义稳定 identity、来源和 presentation；
2. 更新生成器并重新生成 Lua/C++ 目录；
3. 在模块 provider registry 中注册类型、目录校验和动作；
4. 在 SC2 中定义同步/请求语义并更新 golden vectors；
5. 在 AddOn 中增加页面、过滤和错误状态；
6. 更新 schema 或迁移（仅在确实需要时）；
7. 分别记录静态检查、服务端运行、客户端功能和视觉验收结果。

若变更只涉及镜头参数，不应顺便修改收藏 identity、协议或数据库。

## 8. 安全与发布边界

- 仓库不分发 `Wow.exe`、DLL、MPQ、WDB 或从客户端提取的模型/贴图；
- 客户端文件必须由使用者从自己的合法客户端构建；
- AddOn 与模块使用匹配的生成目录和 hash；
- 数据库变更先备份，并保留回滚 SQL/恢复路径；
- “能编译”“服务器能启动”“客户端功能可用”“视觉构图通过”是四种不同状态；
- 镜头调整必须附真实客户端截图，构建成功不能代替视觉验收。

安装与构建入口见仓库根目录
[`README.md`](../../README.md)、[`docs/INSTALLATION.zh-CN.md`](../INSTALLATION.zh-CN.md)
和 [`docs/BUILDING.zh-CN.md`](../BUILDING.zh-CN.md)。
